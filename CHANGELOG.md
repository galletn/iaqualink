## 3.0.0-rc.2 — 2026-08-11

Second release candidate for the 3.x line. **Pre-release** — toggle "Show beta versions" in the integration's HACS panel to install it. Everything in `3.0.0-rc.1` still applies; the notes below are the diff since then.

Most of this release came from capturing real payloads from four live robots (2× `vr`, 2× `cyclonext`) rather than from reading code. Several long-standing assumptions turned out to be wrong, and a few sensors had never worked.

### 🐛 Fixed (user-visible bugs)

- **Cyclonext ±15-minute adjustments now move the remaining-time sensors** (issue #92). The cloud reports the adjustment on cyclonext, but the parser never read it, so a cycle extended in the iAquaLink app — or with this integration's own buttons — kept its original end time. Affects CNX / RE / EvoluX models.
- **Cyclonext now reports its cleaning mode.** The `Fan Speed` sensor read `Unknown` permanently and the vacuum entity's reported speed never reflected the cloud, even though setting the mode worked.
- **"Wall only" no longer appears on VR robots that don't support it.** Issue #76 fixed this for cyclonext by hard-coding the list; the same fault remained for `vr`. Capability varies _within_ a family — of two live VR robots, only one advertised a waterline preset — so the list is now built from what each device actually advertises. If you have been picking a mode that the robot silently ignored, it will now be absent instead.
- **Smart-cycle duration no longer reads 0 minutes** on a robot that hasn't completed a smart cycle yet. The cloud leaves the learned duration at `0` until the first smart run, so time-remaining showed zero for the whole cycle.
- **Cycle durations are now looked up by name.** The old positional lookup was correct only by accident of the order the cloud happened to send its fields in; any reordering would have silently shifted every duration.
- **Cyclonext no longer shows a Temperature sensor** (issue #81). Neither captured cyclonext reports a temperature at all, so it could only ever read `Unknown`.
- **Far less log noise.** A "Fan speed mismatch" warning was emitted on every update — roughly every 10 seconds, about 8,600 lines a day — for any robot in a mismatched state. It is now logged once per distinct mismatch.
- **Model detection no longer depends on scraping a vendor website.** The page it parsed stopped rendering results server-side some time ago, so that lookup had been returning "Unknown" for every input. Models are now resolved offline from the cleaner part number, which also means the integration no longer contacts any site other than the iAqualink cloud. An unrecognised part number now shows as `Unknown (WR0xxxxx)` — please report that string so the model can be added.

### ✨ Added

- **Four diagnostic sensors**, grouped under _Diagnostic_ on the device page: `Firmware Version`, `Error Code`, `Diagnostic Code`, and `Last Cloud Contact`. The last is the most useful for troubleshooting: the `Status` sensor can say "connected" but cannot tell you the robot has been silent for two hours.
- **Richer diagnostics download**: equipment part numbers, partially-redacted component serials, and the capability list the cloud advertises for your device. Attaching this to an issue now usually removes the need for any follow-up questions.
- **`tools/capture_payload.py`** — a maintainer/contributor script that prints a redacted payload plus a field-type report, replacing the hand-written Postman walkthroughs previously needed for issue triage. Reads credentials from a local, git-ignored file.

### 📝 Notes for testers

- The new sensors appear automatically. They are Diagnostic-category, so they sit in a separate section rather than among the controls.
- **Issue #100 (cyclonext stuck "Idle" while cleaning) is _not_ confirmed fixed.** Both captured cyclonext robots report the relevant field as an integer, which rules out the type mismatch that both the reporter and I suspected. A defensive guard is in place, but the root cause is still unknown — if you can reproduce it, a capture taken _while the robot is actively cleaning_ is the missing piece.
- Cyclonext `Diagnostic Code` may read `Unknown` on some models: the RE 4600 iQ omits the field while the CNX 50 iQ reports it. It is kept rather than hidden so the models that do provide it aren't penalised.
- `cs` and `sk` translations for the four new sensors fall back to English and would welcome a native-speaker pass.

## 3.0.0-rc.1 — 2026-05-22

Release candidate for the 3.x line. Consolidates the v2.5.1 → 3.0.0 release notes so testers see the full diff from the last stable in one place. If RC testing surfaces no regressions, this content becomes the `v3.0.0` release notes as-is. **Pre-release** — HACS users on the default channel will not see this version; toggle "Show beta versions" in the integration's HACS panel to install it. **Minimum Home Assistant raised to `2026.3.0`** (via `hacs.json`).

### ⚠ Breaking changes (read before upgrading)

- **Sensor state values are now lowercase snake_case** (`cleaning`, `floor_only`, `connected`) instead of title-cased English (`Cleaning`, `Floor only`, `Connected`). Templates and automations doing `is_state(sensor.x_activity, 'Cleaning')` need to switch to `'cleaning'`. HA's frontend still renders localized text via the new translations.
- **Timestamps are now aware-UTC** (`+00:00` suffix on ISO output) and the three TIMESTAMP sensors (`cycle_start_time`, `estimated_end_time`, `last_online`) declare `device_class=TIMESTAMP` — they render in your local timezone in the UI. Templates parsing the raw string should use `as_datetime()` instead of string slicing.
- **Vacuum entity friendly name** is now the device-registry name only (no English suffix). If you renamed the device card via the UI without re-running the config flow, the vacuum entity's display name shifts to match.
- **Integration domain renamed** `iaqualinkRobots` → `iaqualink_robots` (snake_case, HA convention). Existing config entries auto-migrate; entity_ids and history are preserved.

### 🐛 Fixed (user-visible bugs)

- **VR robots no longer auto-restart** for a second cycle after natural completion (issue #89, PR #94 by @flimzy). Cyclonext / cyclobat / vortrax / i2d are unaffected — the bug was vr-specific.
- **Cyclonext "Walls only" no longer shows** in the cleaning-mode dropdown on CNX 30 iQ / RE 4400 iQ / RE 4600 iQ (issue #76). Cyclonext now correctly exposes only `floor_only` + `floor_and_walls`.
- **Cyclonext fan-speed changes from HA now reach the device** (issue #76, second half). Previously the command silently no-op'd because of a key-style mismatch; the entity remembered the local change but the robot stayed on its previous cycle.
- **Cyclobat now exposes all 4 of its real cleaning modes** (`wall_only`, `floor_only`, `smart_floor_and_walls`, `floor_and_walls`) instead of an i2d-shaped 3-entry list.
- **i2d_robot `stop_cleaning`** no longer double-sends the stop command.
- **`reduce_fifteen_minutes` button** no longer always reads `stepper=0`; it now indexes the active stepper like `add_fifteen_minutes`.
- **Remote-control button names now render in your HA language** (issue #79) — Forward / Backward / Rotate Left/Right / Stop / Add 15 Minutes / Reduce 15 Minutes for cs, de, es, fr, it, nl, pt, sk + English fallback.
- **Stop + immediate restart no longer rolls the UI back to "idle"** for ~3 s before the next poll catches up.
- **TIMESTAMP sensors render "Unknown" on failure paths** (no-data / parse error / never-cleaned) instead of a misleading "right now" instant or "55 years ago" 1970-epoch.
- **Newer HA cores no longer reject the manifest** as `extra keys not allowed @ data['homeassistant']`.
- **Stale-token reauth**: a password change in the iAqualink app now triggers HA's reauth prompt instead of looping silently. REST 401s retry once with a forced token refresh before tripping reauth.
- **Device card `Model` field** now shows the device-type family (`i2d_robot`, `cyclonext`, `vortrax`, `cyclobat`, `vr`) when the cloud hasn't returned a specific model name — was `"Hidden"` or `"Unknown"` before.
- **All entity platforms (vacuum / sensors / buttons) now group under a single device card** in Home Assistant, with consistent `name` / `manufacturer` / `model` / `sw_version` across platforms.

### ✨ Added

- **Reauth flow** in the config flow (story P4): when authentication fails, HA's "Reauthentication required" notification opens a password-only form that updates the entry in place — entity IDs, history, area assignments, and automations are preserved.
- **Repairs flow for the legacy-service behaviour change** (story P8): if your pre-3.0 automations called `iaqualink_robots.remote_forward` / `…remote_stop` / etc. (which silently failed pre-3.0), HA now surfaces a one-time notification on first post-3.0 setup so you can verify those automations still do what you intended (because post-3.0, the services actually move the robot).
- **`Include seconds in time-remaining display` option** in the config flow (default on; turn off via Settings → Devices & Services → Configure to cut ~20× the activity-log spam during long cleaning cycles).
- **Config flow rejects duplicates**: re-adding the same robot now aborts with `already_configured` instead of forking a second coordinator. Multi-robot-per-account users can still add new robots by re-running the user flow with the same credentials — only new robots are offered.
- **Config flow rejects empty/whitespace serials**: prevents the old M13 bug where your email got frozen as the entity unique_id.
- **Diagnostics dump** with credential redaction (Settings → Devices & Services → ⋮ → Download diagnostics — useful for issue reports).
- **Typed WebSocket payload validation** (story P12): the integration now logs an actionable WARNING when the iAqualink cloud silently changes its payload shape, instead of swallowing the drift as a silent KeyError.

### 📝 Migration / manual notes

- **HA minimum raised to `2026.3.0`** via `hacs.json`. Users on older HA will see the version greyed out in HACS — upgrade HA or stay on 2.5.1.
- **Templates parsing timestamps** need `as_datetime()` instead of raw string parsing (see Breaking changes #2).
- **Templates comparing sensor states** to `'Cleaning'` / `'Floor only'` / `'Connected'` need to switch to lowercase keys (see Breaking changes #1).
- **No manual config-entry deletion is required**: every domain rename / schema bump (C7, M17, P3) auto-migrates on next setup.

- **48-story refactor pass** — 46 shipped, 2 backlog (R30 stabilizer-drop is gated on a 4-week production soak after Epic 4; R26-followup compaction is the natural next refactor). Highlights: config-flow hardening (C2/C6/C7/M12/M17/M18/M19/H9a/H9b/P4), refresh-storm reduction (C4-cmd/C4-ws/H6/H7/H10/P10), per-device strategy refactor (R25 × 5 families), `coordinator.py` god-file split (R26: 3566 → 704 + `client.py` + `parsing.py` + `protocols/`), and full `mypy --strict` clean across the package (P6) with a `py.typed` marker.
- **~681 tests** + flake8 + `mypy --strict` + hassfest on every push (GitHub Actions, `ubuntu-latest`).
- **Translations completeness**: all 9 locales (cs / de / en / es / fr / it / nl / pt / sk) have full key coverage with English fallback where native translations haven't been contributed yet (PRs welcome).

### Added

- **Coordinator lifecycle hardening (story P10 + review follow-up).** `coordinator.cleanup()` is the path Home Assistant takes on every entry reload — adding a config entry, removing one, or reloading after an OptionsFlow toggle. Pre-P10 it called `_stop_websocket_listener()` (which already cancelled + awaited the WS task) and `client._close_websocket()` (which already closed the persistent `_ws_session` + `_ws_connection`), but with two latent risks: (a) `_stop_websocket_listener` awaited cancellation **without a timeout** — a listener task that swallowed `CancelledError` would deadlock `async_unload_entry` indefinitely; (b) `vacuum._delayed_refresh()` was scheduled via `asyncio.create_task(...)` directly, making it a true fire-and-forget that would survive entry unload and try to refresh a torn-down coordinator. P10 closes both, and the **3-layer adversarial code review** (Blind Hunter + Edge Case Hunter + Acceptance Auditor) of the initial commit `c762b52` surfaced 11 follow-up patches — all applied in the same Unreleased window so the user-facing contract is the final, hardened shape: (1) `_stop_websocket_listener` wraps the await in `asyncio.wait_for(..., timeout=5.0)` and logs WARNING on timeout; (2) a new `_pending_tasks: set[asyncio.Task]` plus the public `schedule_task(coro)` helper (renamed from `_schedule_task` post-review — it's part of the cross-module coordinator-entity contract) tracks every fire-and-forget task, with self-deregistration via `add_done_callback`; (3) `_cancel_pending_tasks` cancels every task first then awaits the *batch* under a SINGLE 5 s `asyncio.wait` ceiling (review F2-HIGH: pre-review the per-task sequential 5 s wait would blow HA's 60 s integration-unload budget at N≥12 stuck tasks); (4) `cleanup()` is now idempotent — a `_cleanup_done` re-entry guard short-circuits the second call if HA races two unloads (review F4); (5) `client._close_websocket()` is also wrapped in `asyncio.wait_for(..., timeout=5.0)` — symmetric with the other two phases — so a stuck TLS shutdown can't strand unload (review F3); (6) done-task exceptions are explicitly retrieved via `task.exception()` so Python's `Task exception was never retrieved` GC warning doesn't fire from a `_delayed_refresh` that raised mid-flight (review F5); (7) `_cancel_pending_tasks` re-raises `CancelledError` when the *outer* `cleanup()` is being cancelled (e.g. HA hard shutdown), so the cancel propagates correctly instead of being silently swallowed (review F6); (8) `_pending_tasks` is `.clear()`-ed unconditionally at the end of cancellation so the post-state matches the log message (review F7). `vacuum.set_fan_speed` routes its `_delayed_refresh` through `coordinator.schedule_task(...)` — the only fire-and-forget producer in the integration today; The HA-private `_listeners` registry is internal to the `DataUpdateCoordinator` base class and may change shape on any HA minor release; the manual reach-through was a latent break risk. `_immediate_refresh` is deleted entirely; `_handle_realtime_update` now calls `await self.async_request_refresh()` which goes through the proper lock, invokes the same listener-notification path, and honours HA's default request-refresh debouncer (`cooldown=10s`, `immediate=True` — the first call fires the refresh synchronously, subsequent calls within 10 s coalesce into a single trailing refresh) which collapses rapid websocket-event bursts into a single update — a desirable property the old loop did not have. A new AST-based test in `tests/test_coordinator.py` walks every `.py` file in the package and fails CI if `self._listeners` reach-through is ever reintroduced.

### Fixed

- **Stop + immediate-restart no longer rolls the UI back to "idle" (story H6).** Pre-H6, when the user pressed stop and then immediately restarted cleaning, the live `activity == "cleaning"` from the next cloud poll was silently overwritten back to `"idle"` by the queued reset from `stop_cleaning`. The integration's state would lie about what the robot was actually doing until the *next* poll cycle re-fetched. H6 makes the apply state-aware: the new `AqualinkClient._apply_pending_stop_reset` helper consults `data["activity"]` and discards the reset (without clobbering live state) if the cloud has already moved past idle. Also defends against the "stale zombie reset" path — a queued reset that never landed (long disconnect, network drop) and would otherwise apply minutes later — by pairing the values dict with a `_pending_stop_reset_at` timestamp and expiring it after `PENDING_STOP_RESET_MAX_AGE_SECONDS` (10 s, tunable via the new constant in `const.py`). PR #94's natural-completion detector continues to work unchanged — the gate it uses (`not client._pending_stop_reset`) reads the same dict-or-None truthiness it always has; the timestamp is a private contract between `stop_cleaning` and `_apply_pending_stop_reset`.

### Fixed

- **VR robots no longer auto-restart for a second cycle after natural cleaning completion (issue #89, PR #94 by @flimzy).** On Polaris VRX IQ+ and other vr-family devices, finishing a cleaning cycle naturally (without a manual stop) left the iAqualink cloud's `desired.state = 1` (cleaning). The cloud detected the mismatch against the robot's reported idle state and dispatched a command to restart the robot, kicking off another full ~2-hour cycle immediately. A new `AqualinkClient.clear_desired_state()` POSTs `desired.equipment.robot.state = 0` via the existing `setCleanerState` action — the same payload `stop_cleaning` already used for vr, so the cloud-side contract is unchanged. The coordinator's `_async_update_data` detects a `cleaning → idle` transition between `_last_data` and the freshly fetched status — gated on `_pending_stop_reset` being unset so it only fires on **natural** completion, not on a user-initiated stop — and calls the clear. Currently scoped to `_device_type == "vr"`; other device types (vortrax / cyclobat / cyclonext) early-return until users report the same symptom. Regression test locks in that a `cleaning → idle` transition triggers the clear and a `cleaning → cleaning` does not.
- **`stop_cleaning` no longer double-sends the stop command on i2d_robot devices.** A stray return indent in the i2d_robot branch let control fall through after the first POST so the same `_post_command_i2d` invocation fired twice. The second call could no-op or, on a slow cloud round-trip, race with the device's transition to idle and surface as an unexpected error. The branch now returns cleanly after the single POST.
- **`reduce_fifteen_minutes` button no longer always reads `stepper=0`.** The button delegated to a nested dict lookup that hardcoded the stepper index to `0` instead of indexing on the current device's active stepper, so on devices where the stepper lives at a non-zero index the "−15 min" button would either no-op or apply to the wrong stepper. Lookup now mirrors `add_fifteen_minutes`'s symmetric path.
- **Integration now loads under newer Home Assistant cores that reject `extra keys not allowed @ data['homeassistant']` in custom-integration manifests.** Recent hassfest versions in current HA cores rejected the top-level `homeassistant` field in `custom_components/iaqualink_robots/manifest.json` as a hard error, refusing to load the integration. That field is reserved for **core** HA integrations (it signifies which HA version contains the integration); custom integrations declare HA-version compatibility via different mechanisms. The invalid field has been removed.
- **Remote-control button names now render in your Home Assistant UI language (issue #79, story P11).** The seven remote-control buttons (Forward / Backward / Rotate Left / Rotate Right / Stop / Add 15 Minutes / Reduce 15 Minutes) previously displayed in English regardless of HA's language setting because [`button.py`](custom_components/iaqualink_robots/button.py) had its `_attr_translation_key` assignment commented out and a hardcoded English `name` property took precedence. The fix uncomments the translation_key wiring, removes the legacy name property, and adds the class-attribute `_attr_has_entity_name = True` — HA now composes friendly names as `<device-name> <localized-button-name>` for every locale (cs / de / es / fr / it / nl / pt / sk, plus English fallback) using the translations already present in [`translations/*.json`](custom_components/iaqualink_robots/translations/). No translation strings were added; they were dead before.
- **Vacuum entity now follows HA 2024+ entity-naming (issue #79, story P11).** The main vacuum entity used the legacy `name` property pattern, surfacing a friendly name that bypassed HA's translation system. The vacuum class now declares `_attr_has_entity_name = True` + `_attr_name = None` (class attributes), and the legacy `name` property is gone. With `_attr_name = None` the entity is treated as the primary entity for the device — its friendly name is just the device-registry name (the user-typed entry title), no English suffix appended. The previously-set `_attr_translation_key = "fan_speed"` (which pointed at translation keys hassfest had rejected and HA's frontend didn't consume) is also removed. Fan-speed *value* translations (the "Floor only" / "Wall only" dropdown options) remain English-hardcoded in [`sensor.py::fan_speed_display_map`](custom_components/iaqualink_robots/sensor.py); doing those properly requires the `state_attributes.fan_speed.state.<value>` translation shape and is left to a follow-up. The vacuum constructor's `device_name` parameter is dropped (was only used by the removed `name` property); call sites simplified accordingly. **Heads-up for upgrades:** the vacuum entity's friendly name now derives from the device-registry name only (the config-entry title). If you previously customized the device-registry name via the HA UI without re-running the config flow, your vacuum entity's friendly name will update to whatever the device-registry name currently says. Fresh installs and users who never renamed the device card see no change.
- **TIMESTAMP sensors render "Unknown" on no-data / parse failure / never-cleaned, not a misleading "right now" instant (H8 review follow-up).** Post-H8 the three TIMESTAMP-classed sensors (`cycle_start_time`, `estimated_end_time`, `last_online`) emitted `dt_util.utcnow()` from three failure paths: the no-payload websocket branch wrote the string `"unknown"` (incompatible with `device_class=TIMESTAMP`); the four per-device-type exception-fallback blocks wrote `utcnow()` (made the sensor display "cycle started a few seconds ago" every poll during parse failures); and `stop_cleaning` reset values wrote `utcnow()` (made the sensor display "stopped at &lt;local time&gt;" which looked like a fresh start). All five paths now write `None`, so HA renders "Unknown" — the honest signal. A bonus `if timestamp > 0:` guard around the four `dt_util.utc_from_timestamp(robot_data['cycleStartTime'])` calls also prevents the "1970-01-01" cycle-start render for never-cleaned robots from being interpreted as "55 years ago" by HA's TIMESTAMP frontend. Additionally `add_minutes_to_datetime` now `raise TypeError` (not `assert`) on a naive datetime so the fail-fast guard survives `python -O` / `PYTHONOPTIMIZE=1` deployments.
- **Timestamps the integration produces are now timezone-correct (story H8; breaking change for templates that parse the previous naive-local ISO strings).** Every datetime the integration emits to Home Assistant — `cycle_start_time`, `estimated_end_time`, `cycle_end_time`, `last_online`, and the JWT-expiry/model-fetch-backoff internals — is now an aware-UTC datetime instead of a naive-local ISO string. The `cycle_start_time`, `estimated_end_time`, and `last_online` sensor entities now declare `device_class=TIMESTAMP`, so HA's frontend renders them in the user's local timezone instead of as a raw string. Remaining-time arithmetic in `_calculate_times` is now smooth across DST transitions (the prior naive `datetime.datetime.now() - cycle_end_time` math could jump by an hour at spring-forward / fall-back). All sites use `homeassistant.util.dt.utcnow()` / `dt_util.utc_from_timestamp()`; the `add_minutes_to_datetime` helper now asserts its input is tz-aware and fails fast at the helper boundary on a naive datetime. Existing entity *history* stored with the wrong offset is left as-is — new data accumulates correctly going forward. **Template authors**: if you have an automation that parses `states.sensor.<robot>_cycle_start_time.state` as an ISO string, the value now includes a `+00:00` UTC offset (and renders in local time via `device_class=TIMESTAMP`). Template comparisons against `now()` should use `as_datetime()` rather than string slicing.
- **Authentication failures now raise `ConfigEntryAuthFailed` so HA dispatches reauth (story H9b).** Previously, when the iAqualink cloud returned HTTP 401 on a REST call (`get_devices`, `get_device_features`, `post_command_i2d`), the exception bubbled into the coordinator's generic update-failure ladder and the integration kept retrying with stale credentials until `_consecutive_failures` exhausted — no "reauth required" notification ever surfaced. A new internal `AuthFailedError` marker is now raised on `response.status == 401`; the coordinator converts it to `homeassistant.exceptions.ConfigEntryAuthFailed` so HA stops polling and dispatches its reauth handler. The fragile `"401" in str(e)` substring check on the websocket reconnect path is replaced by a typed `aiohttp.WSServerHandshakeError.status == 401` check. Also: command-time WS 401s (in `set_cleaner_state` / `get_device_status`) now surface to reauth instead of being swallowed by the broad-except retry ladder, and `discover_devices` failures during config flow now show `invalid_auth` for credential errors (was previously misclassified as `cannot_connect`).
- **Cognito-side credential rejection now surfaces reauth (story H9b sign-off P1).** The auth endpoint itself (`send_login`) was previously the one credential-rejection path the 401-wrapper missed. When the user rotated their iAqualink password and the coordinator retried `_authenticate(force=True)`, Cognito returned a `NotAuthorizedException`-shaped body that `_authenticate`'s dict accesses fell over with `KeyError` — the coordinator broad-except absorbed it as transient noise and reauth never fired. `send_login` now raises `AuthFailedError` on response status 401, 403, or non-JSON content type; `_authenticate` translates any remaining unexpected-body-shape `KeyError`/`TypeError` to `AuthFailedError` as well. End result: a password change in the iAqualink app now always surfaces HA's reauth prompt.
- **REST 401s now retry once after a forced token refresh before tripping reauth (story H9b).** Matches the spec's Risks/Mitigation clause: a transient cloud 401 (stale token, brief Cognito hiccup) no longer immediately surfaces a "reauth required" notification. The retry uses `_authenticate(force=True)` to bypass the local recheck and force a real Cognito round-trip — necessary because a cloud-side revocation looks locally-valid until the response says otherwise. Only the second consecutive 401 raises `AuthFailedError`.
- **Config flow now supports reauthentication without losing entity history (story P4, bundled with H9b per the spec's pair-land Dependencies line).** When `ConfigEntryAuthFailed` fires (typically after a password change), Home Assistant shows a "Reauthentication required" notification. Clicking it presents a password-only form (email is shown as read-only context). Submitting a valid new password updates the entry in place — `unique_id`, entity_ids, area assignments, automations, and history are all preserved. Invalid credentials re-show the form with `invalid_auth`; network failures show `cannot_connect`. Translation keys added (English fallback for non-English locales; native translations welcome via PR).
- **Reauth flow is defensively robust against HA edge cases (story H9b sign-off).** The previous code used `assert self._reauth_entry is not None` to guard against a deleted-entry race, which is stripped under `python -O`. The flow now aborts cleanly with `reauth_unavailable` (new translation key) if the entry has been deleted between dispatch and form display. The password form enforces a min length of 1 locally instead of round-tripping empty submits to Cognito. A failed `async_reload` post-update is now logged as a WARNING instead of an unhandled exception — HA retries on the next coordinator cycle.
- **Wrong fan-speed list exposed for cyclonext robots (issue #76).** The CNX 30 iQ, RE 4400 iQ, RE 4600 iQ and other cyclonext-family devices were showing a non-functional "Walls only" cleaning mode added in 2.4.2. Cyclonext only supports `floor_only` and `floor_and_walls` on the cloud side, so picking "Walls only" left the entity state forked from the device. The fan-speed-list assignment in `vacuum.py` now branches per `device_type` and mirrors the per-type `cycle_speed_map` in `coordinator.py::_set_other_fan_speed`. Also tightens cyclobat to expose all 4 modes it actually supports (`wall_only`, `floor_only`, `smart_floor_and_walls`, `floor_and_walls`) instead of an i2d-shaped 3-entry list that hid `smart_floor_and_walls` and offered the non-existent `walls_only`. i2d_robot is unchanged — `walls_only` (plural) is a genuine i2d "waterline only" mode (0x04), distinct from `wall_only` (singular) used by vr/cyclobat.
- **Fan-speed changes from Home Assistant no longer propagate to cyclonext robots (issue #76).** Independent of the wrong-list bug above. The cyclonext branch of `AqualinkClient._set_other_fan_speed` keyed its `cycle_speed_map` by display-name strings ("Floor only", "Floor and walls") even though `vacuum.py::async_set_fan_speed` forwards the snake_case translation key. The lookup never matched, `request` stayed `None`, and the command fell through to a silent `{"success": False, ..., "error": "No valid request generated"}` return — the HA entity recorded the new fan_speed locally but no cloud call was made, leaving the device on its previous cycle. Reproduced by the RE 4400 iQ user comment on issue #76. Map keys now match the snake_case translation keys the rest of the integration uses.
